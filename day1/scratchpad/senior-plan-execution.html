Senior Engineer Workflow · order_processing.py

Plan Mode & Execution Mode

How a senior engineer would actually think through "production Python OOP with design principles" before writing code, and how that plan carries into execution — mapped against what this session did.

01 · Plan mode — design thinking

Discover

Frame the problem

"OOP + design principles" is underspecified — pick a domain with real variability (payment methods, discount rules) so SOLID has something to bite on, not a toy Animal/Shape hierarchy.

Model the domain

Order, LineItem as entities/value objects; OrderStatus as an explicit state machine (PENDING→PAID→SHIPPED, or CANCELLED) instead of loose booleans.

Design

Find the seams

What will change independently? Payment provider, discount policy, notification channel. Each seam becomes an abstraction, not an if/elif ladder.

→ drives OCP/DIP

Assign single responsibilities

OrderService orchestrates only; inventory, payment, and notification each get their own class so a change to one never forces a change to another.

→ drives SRP

Pick patterns by fit, not by name-dropping

A pattern only earns its place if removing it makes the code worse. See rationale table below.

De-risk

Define the failure model

What happens if payment fails after inventory is reserved? Plan the rollback (release stock) before writing the happy path.

Decide what's testable

External SDKs (payment gateways) get wrapped behind a Protocol so tests never hit the network.

Flag correctness traps

Money uses Decimal, never float; state transitions are validated, not assumed.

02 · Execution mode — building it

  1. 1

    Implement the plan as code done

    Entities, abstractions, and concrete strategies written in the order the plan laid out — domain first, seams second.

  2. 2

    Compile done

    python -m py_compile order_processing.py — catches syntax errors before anything runs.

  3. 3

    Execute the golden path done

    Ran the demo order end-to-end — this is what a plan document alone can never verify.

  4. 4

    Fix what execution exposed done

    A real run surfaced a datetime.utcnow() deprecation warning the plan never anticipated — fixed and re-verified clean.

  5. 5

    Unit tests for the failure paths not yet in this session

    Insufficient stock, declined payment, illegal status transition — the plan's "de-risk" step defined these; a senior engineer would test them explicitly, not just the happy path.

  6. 6

    Static checks & review not yet in this session

    mypy/ruff plus a second-reviewer pass before this would actually ship.

TAKEAWAY

Plan mode's value here isn't the diagram — it's forcing the failure model and the seams to be decided before code, so implementation is transcription, not discovery. This session skipped the explicit sign-off step (steps 3–4 in Plan Mode above) because the design space was small enough to hold in one pass, but the thinking still happened; it just happened inline instead of as a separate artifact you approved first.

Eyeglasses Listing — Frontend & Backend Build

A working two-tier clone of the Lenskart "All Eyeglasses" tile grid: a static HTML/CSS/JS storefront (Task 1) fetching live product data from a Flask REST API (Task 2). Below is the architecture, the running proof, and the source.

Reference What was replicated

Source page: lenskart.com/eyeglasses/promotions/all-eyeglasses.html

Replicated elements: header/nav, breadcrumb, filter rail, sortable product grid, and per-tile brand, rating, price, strike-through original price, discount %, promo code, and color-variant badge.

Architecture How the two tasks connect

The frontend never touches product data directly — it always asks the backend, which is the single source of truth and where filtering/sorting logic lives.

Task 3 Docker & DevOps integration

Both services are containerized and wired together with Compose, plus a CI workflow that builds and smoke-tests the stack on every push.

Backend runs on Python 3.12-slim, exposes :5000, and has a container healthcheck. Frontend runs on nginx:alpine, exposes :80→8080, and renders its API target from an API_BASE env var via envsubst at container start — no rebuild needed to point it at a different backend.

docker compose config — valid

This sandbox has the Docker CLI but no daemon/Desktop installed, so containers couldn't be built or run here. The Compose file was validated statically instead — docker compose config parses and resolves it cleanly (build contexts, healthcheck, network, and port mappings all correct):

$ docker compose config

services:
  backend:
    build: {context: ./backend, dockerfile: Dockerfile}
    healthcheck: {test: [CMD, python, -c, "urlopen(.../api/products)"], interval: 10s, retries: 5}
    ports: ["5000:5000"]
    networks: {lenskart-net: null}
  frontend:
    build: {context: ./frontend, dockerfile: Dockerfile}
    depends_on: {backend: {condition: service_healthy}}
    environment: {API_BASE: http://localhost:5000}
    ports: ["8080:80"]
    networks: {lenskart-net: null}
networks:
  lenskart-net: {name: lenskart_clone_lenskart-net, driver: bridge}

On a machine with Docker running, docker compose up --build in lenskart_clone/ brings up both containers exactly as diagrammed above.

Beyond the build Assumptions, hypotheses & unknowns

Nothing in the original prompt specified a rubric, a data-sourcing policy, or a deploy target — this exercise was built by filling those gaps with judgment calls. Plotted below by how confident that judgment is versus how much it would cost to be wrong.

Assumption — taken as given Hypothesis — informed guess, testable Unknown — not stated, could change the build

Assumptions — treated as given, low risk if wrong

  • A1This is a learning/demo exercise, not a production e-commerce build — so no auth, database, or payment flow was added.
  • A2Mock, hand-written product data stands in for scraping Lenskart's live catalog — avoids ToS/scraping issues and keeps the API deterministic.
  • A3Placeholder images (placehold.co) are an acceptable substitute for real Lenskart product photography.
  • A4A single-user local dev setup is fine — no login, sessions, or multi-tenant concerns.
  • A5A published HTML report with diagrams satisfies "evidence of implementation" better than raw terminal logs or screenshots alone.

Hypotheses — informed guesses, worth confirming

  • H1The "Task 1 / Task 2 / Task 3" phrasing suggests this maps to a structured course or interview assignment with named deliverables per task.
  • H2"Docker devops integration" means containerize + wire with Compose + basic CI — not a full cloud/Kubernetes rollout.
  • H3Wherever this gets run or reviewed next, Docker Desktop (or an equivalent daemon) will actually be available — unlike in this sandbox.

Unknowns — not stated anywhere, highest-impact if wrong

  • U1What the actual grading rubric or success criteria are — a course grader, an interviewer, and a personal project each want very different depth.
  • U2Whether reproducing Lenskart's UI, copy, or branding more literally would run into copyright/ToS limits for a real submission.
  • U3The intended deploy target for "devops integration" — a laptop, a CI runner, a cloud VM, or a Kubernetes cluster all imply different next steps.
  • U4Whether persistence, authentication, or payments are actually in scope, or this stays a read-only catalog demo.
  • U5Whether Docker will be runnable in whatever environment this is next opened in — this sandbox could not confirm the containers actually build.
